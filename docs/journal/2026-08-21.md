# 2026-08-21 — day 21: kept turns on itself, and finds two lies

Today kept audited kept for the first time. It found two defects in its own
verification path, either of which was enough to make every verdict it had ever
printed untrustworthy.

## What the first run said, and why it was fiction

`51 promises · 26 kept · 0 weak · 25 unproven`.

Zero weak, twenty-six kept. On a suite nobody had ever mutation-tested. That
number was too good, and it was wrong twice over.

**The mutated copy was never imported.** kept copies the project into a temporary
worktree, mutates one file in the copy, and runs the bound tests there. But kept
is installed into its own environment, so `import kept` resolved through the
editable path back to the *original* source. The mutation was sitting in a file
nobody read. Measured directly, same mutant and same tests:

    without the worktree on PYTHONPATH:  20 passed
    with the worktree on PYTHONPATH:      5 failed

Every src-layout project is affected. The fix puts the worktree's import root
ahead of anything installed.

**Mutants that never ran were counted as kills.** A mutant that failed to build,
or that came out textually identical to the original, returned `killed=criteria`.
Since `discriminating = killed + missed`, a promise whose every mutant was a no-op
scored 1.0 and reported KEPT on an empty probe. A comment in the source claimed
this "cannot inflate the score". It could, and it did. Such mutants are now marked
`executed=False` and excluded from every count, so the promise reports UNPROVEN
with no mutants — which is the truth.

Both are the failure kept exists to detect, found inside kept. The tool passed its
own test by failing it.

After the fix: `51 promises · 3 kept · 46 weak · 2 unproven`.

## What 46 WEAK actually means

The misses concentrated. Five mutants accounted for most of them; one was charged
against 33 promises on its own.

That one changes `if char == BACKTICK` to `!=` in the lexer's main loop. It looks
catastrophic and is nearly inert: the function it wrongly calls falls back to
ordinary word lexing when it finds no closing backtick, so for any input without a
backtick the token stream is identical. Only REQ-1.8's oracles lex backticked
text, and they fail instantly — which is how kept knows it is detectable, and why
it charges 33 other promises for missing it.

So a promise about markdown headings is marked WEAK partly for not noticing a
lexer change. I spent a while deciding whether that is a defect. It is not. The
question kept asks is not "is this line tested somewhere" but "would this promise's
own oracles notice if it broke", and for those 33 the answer is honestly no: if
REQ-1.8's tests were deleted, that branch would be unguarded and 33 promises would
still report success. Written up as ADR-0006, including the three fixes I rejected
— scoping mutants by module, discarding rarely-killed mutants, and lowering the
threshold to flatter the result.

## Fixed, and not fixed

Two oracles strengthened where the missed breakage was squarely their own business:
`criterion_id` at its one-based boundary, and the EOF test, which counted exactly
one end-of-input token without checking the words were still there. REQ-3.2 went
WEAK → KEPT. Published now: `51 promises · 4 kept · 45 weak · 2 unproven`.

Forty-five to go, and I am not going to pretend they are a morning's work. Each one
needs its own oracle to assert more of what it already executes.

REQ-5.6 and REQ-6.4 have no test at all and say UNPROVEN. I left them that way
rather than inventing a binding.

## Also today

`tests/test_verdict.py` — the rule engine's first unit tests, constructed evidence
and no I/O, carrying the regression test for the manufactured-KEPT bug. The mutation
cache is versioned, and version 1 is discarded wholesale: every entry it held was
recorded under the broken semantics.

CI now runs `kept verify --root . --gate no-regression`, so kept's own number can
only improve without a deliberate decision. 31.6 seconds cold on the whole
repository.

## The thing worth saying out loud

I have been publishing a tool that detects code which only appears to work, and for
three days it only appeared to work. The two bugs were invisible to the test suite,
invisible to coverage, and invisible to me, and the only thing that surfaced them
was pointing the tool at itself and finding a number too flattering to believe.

That is the whole argument for the ledger, and I got to test it the hard way.

## Later the same day: the docs, and one loose end

Published `kept-cli 0.1.0` to PyPI by trusted publishing, then tested the release
the way a user would rather than the way an author would: a fresh Kiro-style project
in a scratch directory, six lines of `pricing.py`, four EARS criteria, three tests,
and `uv pip install kept-cli` from the index. The marker registered with no
`conftest.py`, which is the part packaging could have broken silently.

`0 kept · 3 weak · 1 unproven` in 3.1 seconds — and the findings on six lines of code
are better than the ones in our own fixtures. The criterion about rounding a
fractional penny has no test, and the `+ 99` that implements it is an unpinned line:
change it and nothing in the suite notices. The one promise nobody tested is the one
line nobody guards. That is the entire thesis, accidentally, in a throwaway fixture.

Which is also why it stays a throwaway. `fixtures.md` warns against authoring a
subject that fails interestingly, and I authored that one to fail interestingly. It
is a fine release smoke test and it would be a dishonest demo.

Docs written: the threat model, which is this tool's scrutiny turned on itself and
names the two defects found this morning as live defects rather than as anecdotes;
the capability table, because the resemblance to Kiro's property-based testing is
the most obvious objection to the project and burying it would be cowardly; an ADR
index; and `.kept/config.toml`, so `kept verify` is the whole command in a project
that needs settings.

The one loose end I keep deciding not to close: 45 WEAK verdicts. ADR-0006 explains
why most of them are honest, and the explanation is not the same thing as the work.
